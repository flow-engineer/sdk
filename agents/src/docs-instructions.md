Flow Messaging is one HTTP API ({{base_url}}) for AI agents to hold two-way conversations on Telegram and iMessage (replies only, on lines set up by the Flow team), and on WhatsApp: you can connect your own WhatsApp number (your WhatsApp Business Account and Meta app) with POST /v1/senders and a live key, or on the dashboard's Senders page; the Flow team can still help. If the user asks for WhatsApp, tell them they can connect their own WhatsApp number with a live key, and build and test on simulated WhatsApp conversations or Telegram meanwhile: the code does not change per channel.

Build the app on the REST API. {{mcp.runtime_rule}} In TypeScript or JavaScript, the SDK is `npm install {{package}}`, then `new FlowMessaging()` (reads {{env.api_key}}). In Python, the SDK is `pip install {{python_package}}`, then `from flow_messaging import Flow` and `Flow()` (reads {{env.api_key}}). The Go SDK is not published yet; in Go call the HTTP API directly.

No key yet? If {{env.api_key}} is not set, get a test key with no account in one call: curl -X POST {{base_url}}/v1/sandbox/keys (or npx {{package}} init, which writes it to .env). Save `key` as {{env.api_key}} and `claim_token` as {{env.claim_token}}; both are shown once. It allows {{allowance.anonymous.contacts}} contact and {{allowance.anonymous.messages_per_contact}} messages on the Telegram sandbox and expires after {{allowance.anonymous.key_ttl_days}} days; a person signs in with `npx {{package}} login` (with {{sign_in}}) to keep the app and get {{allowance.signed_in.contacts}} contacts x {{allowance.signed_in.messages_per_contact}} messages. Signed in, live keys (fk_live_...) are made in the dashboard for your own Telegram bot; iMessage lines are arranged with the Flow team.

The hosted MCP server ({{mcp.url}}) is optional, for testing during development. {{mcp.owner_rule}} The command for Claude Code: {{mcp.add.claude}} (run it with {{env.api_key}} set, then restart the client). If its tools are already available to you, use them for sandbox testing.

Authenticate with `Authorization: Bearer fk_test_...` (sandbox) or `fk_live_...` (real contacts). Never put a live key in client-side code.

Reply into a conversation (POST /v1/conversations/{conversation_id}/messages); never pick a channel per message. Switch on `error.type`, not the message text.

Flow Observe ({{observe.url}}, early access) records and grades every conversation of a chat agent. On Flow Messaging it needs no code. On any other channel, send one OpenTelemetry trace per turn over OTLP/HTTP to {{observe.traces_url}} with `Authorization: Bearer ${{env.observe_trace_key}}`, and set `flow.conversation_id` (required), `flow.message_id`, `flow.user_message` and `flow.agent_reply` (the text actually sent) on the turn's span. Keys (trace key `otk_test_...`, CI key `oci_...`) are made by the user on Observe's Setup page at https://flow.engineer/observe after signing in with their Flow login; Observe is in early access, and if it is not on for them, they ask the Flow team ({{team_contacts|or}}). Never invent a key, and never ask the user to paste one into the chat. Test data only until the account is enabled for production. Guide: {{observe.docs}}

Full documentation for agents: {{docs_url}}/llms-full.txt. OpenAPI spec: https://raw.githubusercontent.com/flow-engineer/sdk/main/openapi/openapi.yaml.
